# v0.4 M7 report: Streamable HTTP transport

Lane B (Command Code). Built on `lane-b/v0.4`, merged into `v0.4`.

## 1. Features built

- Dual-era upstream HTTP client (`packages/core/src/http.ts`), commit `9e826d4`. 2026-07-28: POST per message with `Accept: application/json, text/event-stream`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, and `Mcp-Param-{Name}` headers, `=?base64?...?=` sentinel encoding for non-ASCII-safe values, request-scoped SSE parsing (notifications then final response), 202 for notifications, upstream header/body disagreement flagged and the response rejected, JSON-RPC requests pushed on SSE flagged as protocol violations, stream closure = cancellation. 2025-11-25: initialize handshake, `Mcp-Session-Id`, GET SSE stream with `Last-Event-ID`, DELETE on close, modern-server auto-detection from 404/400 + modern JSON-RPC error with synthesized initialize. Both eras refuse any redirect while `Authorization` is set and refuse cross-origin redirects entirely.
- Transparent listener (`packages/core/src/http-listener.ts`), same commit. `/mcp/<serverName>` routes, upstream always from config, localhost binding unless `--allow-remote`, localhost-only `Origin` validation, Palizade bearer token (`X-Palizade-Token`, generated at `init`), client `Authorization` forwarded unchanged only to the configured upstream origin, 401/403/`WWW-Authenticate` passthrough for OAuth discovery, request-body/SSE-line/SSE-event/concurrency/timeout limits.
- Bridge mode: `palizade wrap <server>` for `url` servers keeps stdio on the client side (`HttpBridgeProxy`, same commit).
- Config: `servers.<name>.url` + `headers` with `${ENV}` templates + `protocolVersion` pinning, `http.*` and `listener.*` sections with safe defaults, command/url exclusivity validation (commit `9e826d4`).
- CLI: `palizade serve`, `palizade status [--json]`, `init` token generation, `lock approve`/`doctor`/`install-config` understand url servers (commit `0fadb5a`).

## 3. New policy conditions

None. The transport adds no policy surface; blocked sink behavior over HTTP is identical to stdio because the same `InterceptionEngine` runs in the middle.

## 4. Behavior changes to existing presets

None. Preset files are untouched. Existing stdio configs parse unchanged (`command` is now optional but still accepted; every old config has it).

## 6. `// shortcut:` comments

- `packages/core/src/http-listener.ts` — the listener shares one engine and (for legacy servers) one upstream session per served server name; concurrent legacy clients share the session. Upgrade when per-client sessions are needed.
- `packages/core/src/http.ts` (`collectToolsFromHttpServer`) — the legacy probe path assumes the first non-modern POST is initialize-able; a server that rejects initialize with a plain 400 body falls back to a generic error.

## 7. Not verified against the spec

- The 2026-07-28 streamable-http page was read live and implemented against; the changelog, authorization, and elicitation pages were not fetched during M7 (elicitation specifics belong to M5).
- `Mcp-Param-*` validation on the listener inbound path only checks the standard headers (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`); parameter-header validation is applied to outbound requests from known tool schemas.

## 8. Skipped or partly done

- Request-scoped SSE notifications from a modern upstream are relayed to the client only when the client's `Accept` includes `text/event-stream`; a JSON-only client gets the final response. Notifications are still audited. Documented in README "What Palizade Does Not Protect".
- The listener does not expose a `subscriptions/listen` long-lived relay; the 2026-07-28 subscription stream is treated like any other request-scoped stream (M5 adds the re-lock trigger).
