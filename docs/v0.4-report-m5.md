# v0.4 M5 report: MCP 2026-07-28 support (dual era) on stdio

Lane B (Command Code). Built on `lane-b/v0.4`, merged into `v0.4`.

## 1. Features built

- Era detection per message (`packages/core/src/era.ts`): `_meta["io.modelcontextprotocol/protocolVersion"]` marks 2026-07-28, `initialize` marks the legacy era; the engine records the era per direction in audit metadata.
- Input-required gating (`checkInputRequiredRequests` in `packages/core/src/interceptor.ts`): `resultType: "input_required"` results are inspected; each `inputRequests` entry is gated with the same policy methods the legacy server-initiated requests used — `sampling/createMessage` (default deny via existing presets), `elicitation/create` (approval), `roots/list` (safe). Form-mode elicitations that request sensitive fields (password/API key/token/payment patterns) are denied per spec; URL-mode elicitation URLs go through the egress allowlist and taint checks. Denied requests convert the whole result into a tool error and are audited.
- `inputResponses` on the client's MRTR retry are taint-matched like sink arguments (untrusted and sensitive classes), so tainted content supplied back to the server trips the sink rules.
- `notifications/tools/list_changed` is forwarded to the client and triggers a proxy-side `tools/list` re-lock (`palizade-relock-<n>` synthetic request). Drifted metadata is approval-gated (`m5-relock-gate`), the synthetic response is never forwarded, and every relock is audited with `relock: true`.
- `server/discover` responses are lock-checked and scanned like `tools/list` (known-tool registry updated).
- `subscriptions/listen` responses are scanned through the generic content path.
- `structuredContent` is scanned and taint-registered like `content` text (it was already extracted by the content walker; sanitize/spotlight now applies to structuredContent string fields via `isSpotlightableText`, keeping non-string schema fields untouched).
- `ttlMs`/`cacheScope` on list results are captured in audit metadata; the lockfile is re-verified on every refresh regardless of client caching.
- Preset addition: `approve-elicitation` rule (`elicitation/create` → require_approval) in `default.yaml` and `interactive.yaml` (`strict` already requires approval by default).

## 3. New policy condition

None. MRTR gating reuses existing conditions by mapping to the legacy method names (`sampling/createMessage`, `elicitation/create`).

## 4. Behavior changes to existing presets

- `default.yaml` and `interactive.yaml` gain `approve-elicitation` (require_approval for `elicitation/create`). This gates legacy-era elicitation too, since both eras use the same method name. Documented in `docs/policy.md`.
- Server notifications (`notifications/*`) are now forwarded to the client instead of being silently dropped by the "non-allowlisted server request" block; `tools/list_changed` additionally triggers the re-lock. Documented in `docs/architecture.md`.
