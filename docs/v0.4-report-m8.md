# M8: operability (lane C)

## Features and commits

- `7ec9285`: validation errors. `palizade.yaml`, policy files and `palizade.allow.yaml` report every problem (up to 20) with the YAML path, line number and a one line fix hint, including "did you mean" for misspelled keys and the allowed values for enums. YAML syntax errors report the line. Messages never contain the rejected value. Code: `packages/policy/src/errors.ts` (`SchemaValidationError`, `parseYamlWithSchema`).
- `3100b7c`: `palizade policy check [file] [--json] [--strict]`. Reports schema errors and unknown keys, unreachable rules after a catch-all, conditions that can never be true, an invalid `argument_regex`, duplicate rule ids, and `server`/`tool` values that are not in `palizade.yaml` or `palizade.lock`. Exit 1 on errors (and on warnings with `--strict`). Without a config file it still checks the policy and says that references were not checked. Code: `packages/policy/src/check.ts`, `packages/cli/src/policy-check.ts`.
- `4b735c8`: hot reload of policy, config and `palizade.allow.yaml` for `wrap` and `serve`. Files are polled, validated in full, then swapped into the engine in one assignment. A bad file keeps the previous version, writes a `config/reload` audit event and warns on stderr. Settings that only change on restart are listed in the warning. Code: `packages/core/src/hot-reload.ts`, `InterceptionEngine.reload()`, `LearnedEgress` keep-last-good.
- `1b0d36e`: `palizade status [--json]` now also shows per-server lock state, last seen protocol era (from audit), sandbox, taint counts split into normal and persistent, quarantined sessions, sessions with the Rule of Two armed, and the last 10 blocks. Existing JSON fields are unchanged. Code: `packages/cli/src/status.ts`, `SqliteTaintStore.recordCounts()` and `listSessions()`.
- `0ec22b9`: `palizade learn --from-audit --since 7d [--server <name>]` prints a draft YAML of observed tool classes (skipping ones already set in `palizade.yaml`) and allowlist hosts and emails. It does not suggest destinations seen only in blocked calls or with tainted data; those are listed as comments. It never writes a file. Code: `packages/cli/src/learn.ts`.
- `0001a3f`: optional `metrics.jsonl`, one line per decision with identifiers and counters only. Code: `packages/audit/src/metrics.ts`.
- `f1f979d`: docs (`README.md` commands, Debugging and limits; `docs/architecture.md` Configuration Loading; `docs/policy.md` policy check).
- `b398a79`: shortcut comments.

## Configuration defaults

Both new blocks are optional, top-level nested objects:

- `reload.enabled`: `true` (applies to `wrap` and `serve`; programmatic `createRuntime` callers opt in by passing `configPath`).
- `reload.intervalMs`: `1000` (100 to 60000).
- `metrics`: unset (off). `metrics.jsonl` is required when the block is present and resolves relative to `palizade.yaml`; `metrics.maxBytes`: `67108864` (64 MiB), then the file rotates to `<file>.1`.
- Fixed bounds: reloaded files over 1 MiB are rejected; validation lists at most 20 problems; `status` lists at most 1000 stored sessions; `learn` lists at most 200 entries per list.

## Policy conditions

None added. `policy check` validates the existing conditions.

## Behavior changes for existing users

- Error messages for invalid YAML changed from raw zod output to the path, line and hint format. The original zod message is still part of each line. The thrown error is a `SchemaValidationError`; no code in the repo depended on `ZodError`.
- Running `wrap` and `serve` processes now pick up edits to the policy, config and allowlist without a restart. Before, edits to the policy and config were ignored until restart.
- An invalid `palizade.allow.yaml` edit while running used to fail every sink call closed (`on_error`). With hot reload on (the default), the last valid allowlist stays active and the failure is audited and printed once. With `reload.enabled: false` the old fail-closed behavior is unchanged. An invalid allowlist at startup still fails.
- `palizade status` prints more lines; the JSON output adds fields without renaming any.
- No preset changes.

## Not verified

- Hot reload under `serve` with several url servers was not run end to end; each runtime gets its own reloader through the same `createRuntime` path that the unit test covers.
- Polling was tested on Windows only (the file-watcher test). Linux and macOS use the same `fs.watchFile` API.

## Skipped or partial

- "Impossible conditions" covers empty lists, contradictory or impossible score bounds, and invalid regexes. Combinations that depend on runtime semantics (for example `taint: false` with `tainted_argument_role_any`) are not flagged, to avoid false warnings.
- `status` reports the era configured for each server and the last era seen in audit. It does not query live processes.
- `learn` suggests hosts and emails from the audit `destination` summary. Repository, channel and account destinations are not in that summary, so they are not suggested.
